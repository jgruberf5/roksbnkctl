# BNK 2.4

`roksbnkctl` drives BNK **2.3** and **2.4** from one build. Which one you get is
decided by `bnk.manifest_version` and nothing else — there is deliberately no
`bnk.line` field and no `ROKSBNKCTL_BNK_LINE` override, because a second way to
say which release this is, is a second thing that can disagree with the manifest
being installed.

```yaml
bnk:
  manifest_version: 2.3.0-3.2598.3-0.0.170   # -> the 2.3 line
  # manifest_version: 2.4.0-EA               # -> the 2.4 line
```

The derived value is rendered as a `bnk_line` terraform variable (`"2.3"` or
`"2.4"`), and the modules gate per-release resources with `count` on it. There is
no forked copy of the tree: the 2.4 changes are additive resources, which `count`
expresses cleanly and two copies of a file do not.

> **`2.4.0-EA` carries no build suffix**, where 2.3 versions have four dot/dash
> segments (`2.3.0-3.2598.3-0.0.170`). Anything you write that parses a manifest
> version should key on the `major.minor` prefix rather than the segment count.

## What actually changes

2.4 replaces the data-plane configuration model. It runs the CNEInstance with
`USE_GATEWAY_SETTINGS=true`, and under that flag the CNE controller **ignores**
the `cloud-network-mapping` ConfigMap and the entire `F5SPK*` custom-resource
family that a 2.3 install creates, reading two new CRs instead.

| 2.3 | 2.4 |
|---|---|
| `cloud-network-mapping` ConfigMap | `Infra.spec.networks[]` + `networkAttachments[]` |
| `F5SPKVlan` × 2 | `Infra.spec.networks[type=vlan]` |
| `F5SPKStaticRoute` × N | `Infra.spec.staticRoutes[]` |
| `F5SPKSnatpool` | `GatewaySettings.spec.sourceNATPools[]` |
| `F5SPKEgress` × 2 | `GatewaySettings.spec.egressConfigs[]` + `Infra.spec.egressDefaults` |
| `F5BnkGateway` | `GatewaySettings` (the Gateway's `parametersRef` target) |
| VIP address arithmetic | IPAM allocation, read from `Gateway.status.addresses` |

`roksbnkctl` emits both CRs for you. The addressing comes from the per-zone CIDRs
you already configure — nothing new to fill in for a standard install:

| your existing config | the 2.4 IPAM pool it becomes |
|---|---|
| `ext_vlan_cidr` | `external-vlan-ipam` — TMM VLAN self-IPs |
| `int_vip_cidr` | `vip-listener-ipam` — ingress VIPs |
| `int_snat_cidr` | `egress-snat-ipam` — egress SNAT addresses |

`gateway_egress_mode` means the same thing on both lines: `snatpool` becomes a
`Pool` egress config backed by `egress-snat-ipam`, `automap` becomes an `Automap`
config, and `both` produces both.

### Things 2.4 stops needing

Three of the four items in the 2.4 guide's own "Changes From BNK Release-2.3"
section are *subtractions*, which is easy to miss when reading a list of
additions. On the 2.4 line `roksbnkctl` no longer creates:

- **a separate CIS Helm release** — CIS is integrated into FLO, and
  `externalBigip.enabled` on the CNEInstance is what turns it on;
- **the node-labeler Job** — `app=f5-tmm` labelling is not required;
- **the `macvlan-conf` NetworkAttachmentDefinition** — the product creates its
  own internal NAD as `macvlan-internal` on `dummy0`, owned by the `F5Tmm` CR,
  and that name is reserved;
- **eighteen of nineteen privileged SCC bindings.** FLO grants its components
  what they need, so the install requires one binding rather than nineteen.

> The guide also asks for one privileged SCC binding **per application
> namespace** (`oc adm policy add-scc-to-user privileged -n <ns> -z default`).
> `roksbnkctl` does not create those: it knows the FLO and utils namespaces and
> nothing about where you will run workloads. That one stays an operator step.

## The Trusted Profile

2.4's CNE controller authenticates to IBM Cloud with a **Trusted Profile** and
uses it to write into your VPC — adding the `Infra` IPAM CIDRs as VPC address
prefixes, creating a routing table, and advertising TMM virtual-IP routes to the
transit gateway.

`roksbnkctl` creates the profile, links it to the cluster's service account, and
passes its id to the CNEInstance as
`advanced.cneController.env.CLOUD_TRUSTED_PROFILE`. Two access policies are
attached: **Viewer + Editor on the cluster's VPC**, so the controller can manage
the network objects it creates, and **Viewer on the cluster itself**, so it can
read the topology it next-hops routes against.

Because those IPAM CIDRs become real VPC address prefixes, they must not collide
with what the cluster VPC already allocates — see
[Transit gateway sharing](./09a-transit-gateway-sharing.md).

## Moving between lines

**You cannot flip a deployed workspace from 2.3 to 2.4 in place.** `bnk up` and
`gateway up` both refuse it, and the refusal names the reasons, because none of
them is visible in a terraform plan:

- **GTM object naming differs.** 2.3 writes `server_<tmm_selfip>`; 2.4 writes
  `server_<digitalassetid>_<cluster-name>_<ns>_<ip>`. Those objects live on an
  external BIG-IP — outside the cluster and outside terraform state — so nothing
  here removes them, and leaving both formats in place causes device IP
  conflicts.
- **The network model is replaced, not migrated.** The `F5SPK*` objects a 2.3
  install created are simply no longer read, and they stay on the cluster.
- **The CWC licence secrets survive a teardown** and must be cleared before a
  reinstall licenses cleanly. `bnk down` now removes them for you.

To run 2.4, use a **new workspace and a new install**. Changing
`CLUSTER_IDENTIFIER` on a deployed workspace needs the same manual GTM cleanup,
for the same reason.

## mTLS and the Gateway API bundle

A base 2.4 install works with whatever Gateway API bundle OpenShift ships: its
`crd-installer` logs a graceful skip and leaves the platform's CRDs alone.

**mTLS is the exception.** It needs Gateway API 1.5.0 standard, and installing
that means deleting the OpenShift ingress-operator's
`ValidatingAdmissionPolicy` and its binding — which the platform recreates
quickly, so it is a race. Opt in:

```yaml
bnk:
  gateway_api_mtls: true      # ROKSBNKCTL_GATEWAY_API_MTLS=true
```

Off by default, because deleting a platform admission policy on a cluster that
does not need the newer bundle is a change nobody asked for. Ignored on 2.3,
where that sweep always runs — there the `crd-installer` *does* force its own
CRDs and is blocked without it.

## Per-component settings

> Field specs for everything below live in
> [Chapter 28 — Configuration reference](./28-configuration-reference.md), which is
> generated from the struct and test-checked. The `line` column there says which
> release line each field applies to.

The 2.4 CNEInstance takes an environment list for each of its ~26 components.
Anything not surfaced as a first-class field is reachable through the
passthrough, in YAML or from the environment:

```yaml
bnk:
  advanced:
    tmm:
      env:
        TMM_DEFAULT_MTU: "9000"
    cneController:
      env:
        GSLB_DATACENTER_NAME: "datacenter-eu-gb"
```

```bash
ROKSBNKCTL_BNK_ADV_TMM_ENV_TMM_DEFAULT_MTU=9000
ROKSBNKCTL_BNK_ADV_CNECONTROLLER_ENV_GSLB_DATACENTER_NAME=datacenter-eu-gb
```

An entry here **replaces** the default of the same name rather than adding a
second copy of it — the CNEInstance spec is read by the lifecycle operator, not
by kubelet, so "the last duplicate wins" is not a rule to rely on. That is what
makes this the way to *change* a default rather than only to add to it.

`USE_GATEWAY_SETTINGS` is deliberately **not** the example here, though earlier
drafts of this page used it. `roksbnkctl` sets it on 2.4 itself, because on 2.4
there is no working configuration without it: without the flag the controller
never reads the `Infra` and `GatewaySettings` CRs that `gateway up` applies, and
they sit at `Accepted=Unknown` forever. You can still override it through this
passthrough — that is what the replace-not-append rule buys you — but you should
not have to.

The component name is matched case-insensitively, and one that `roksbnkctl` does
not recognize is passed through rather than refused — the component set belongs
to the product, and this tool should not be the reason a newly shipped one is
unreachable.

## Checking a 2.4 install

`bnk status` reports the CNEInstance's aggregate `Available` condition plus any
component condition that is not `True`, which is what turns a timeout into a
diagnosis:

```
cneinstance:            Available=False (ComponentsNotReady)
cneinstance_not_ready:  F5TmmAvailable=False
```

That distinction matters on 2.4. `CNEControllerAvailable=True` can sit next to
`Available=False` with TMM at 0/3 and nothing passing traffic.

The gate itself is `CNEControllerAvailable` on **both** lines, and deliberately
so: waiting on the aggregate at the gate deadlocks 2.4, because the aggregate
cannot go True until the License CR exists and the License CR is created after
the gate. The aggregate is checked separately, after licensing, which is where
it can actually be satisfied.

> If a 2.4 install looks broken in a way that has nothing to do with what you
> changed, check the `License` CR first. The controller refuses to run *any*
> resource controller until it is Active, logging `License is not enabled.. skip
> Resource controllers`.

`gateway status` reports the `Infra` and `GatewaySettings` CRs alongside the
Gateway, and reads the **IPAM-allocated** VIP from the Gateway's status — on 2.4
there is no address to compute, only one to read.

## Support status

2.4 is **verified against `2.4.0-EA`**: `bnk up` reaches all eighteen CNEInstance
conditions with TMM at 5/5 and the licence Active, on a single-NIC OCP 4.20
cluster with connected licensing.

What that run covered, and what it did not, because the difference matters:

| | |
|---|---|
| exercised | `bnk up` on an adopted cluster — manifest `2.4.0-EA`, FAR `repo.f5.com` with the non-GA service account, three workers, single-NIC, connected licensing |
| exercised | the **gateway phase** — `gateway up` applies `Infra` and `GatewaySettings`, and both reach `Accepted`, `ResolvedRefs` and `Programmed` = `True`, with the CNEInstance still 18/18 and the licence still Active afterwards |
| **not** exercised | mTLS, multi-NIC, disconnected licensing, `EgressGateway` CRs, and the contract boundary |

Running the gateway phase is what found the three defects that made it
impossible before it was run: the gateway plan failed outright on 2.4, nothing
set `USE_GATEWAY_SETTINGS` so no controller ever reconciled the CRs, and the
`cneinstance_advanced_env` override meant to let you set it by hand was read by
no terraform at all. None of the three was visible in the source — the third
least of all, since the variable's name appears everywhere it should.

2.4 EA is **single-NIC throughout** — one NetworkAttachmentDefinition, one
`external-vlan` network in the `Infra` CR, and no second data-plane interface
anywhere. An earlier expectation that 2.4 would bring multi-NIC is withdrawn, and
the verified run was single-NIC, so it is evidence for single-NIC and nothing
else.

`support_matrix.yaml` records the same thing in the same terms. Its rule is worth
repeating, because it is what keeps that file useful: a cell with no coverage is
a claim nobody has checked.
