## Top-3 experiments for this session (priority order from audit §5.4)

### Experiment 1 — Verify PCI BDF mapping (~5 min, lowest cost)

Our `PCIDEVICE_INTEL_COM_ENS{7,8}` env vars hard-code `0000:00:0{7,8}.0` assuming Nitro hypervisor maps device-index N → 00:0N.0. If wrong, mapres reads garbage memory → SIGSEGV.

```bash
# After up reaches Phase 11/16:
kubectl debug node/<tmm-node> --image=busybox --profile=sysadmin -- chroot /host sh -c \
  'for i in $(ls /sys/class/net/ | grep "^ens"); do
     bdf=$(readlink /sys/class/net/$i/device | sed "s|.*/||")
     echo "$i -> $bdf"
   done'
```

Compare against `state.env`'s `EXTERNAL_PCI` (`0000:00:08.0`) and `INTERNAL_PCI` (`0000:00:07.0`). If mismatched, Phase 17 needs to read BDF post-attach via SDK rather than hardcoding.

### Experiment 2 — cgroup v2 vs v1 (~15 min, requires LT userdata change)

AL2023 defaults to cgroup v2; AL2 uses v1. BNK TMM image may expect v1 for hugepages accounting / CPU pinning. Test by appending kernel arg to launch-template userdata: `systemd.unified_cgroup_hierarchy=0`. If TMM stops crashing on a fresh cluster, we have root cause + permanent fix.

Where to add: `internal/aws/phases/phase10_nodegroup.go` `bnkLaunchTemplateUserData` — the GRUB cmdline modification needs to happen pre-boot. Probably via `cloud-init` or by editing `/etc/default/grub.d/`. Test in a feature branch.

### Experiment 3 — First-boot clean cores (~25 min, full teardown+up)

The crashagent's "idle mode" is fed by prior crash residue. On a TRULY fresh cluster (no stale `/shared/core` on the host), does TMM segfault on its FIRST mapres run, or only after the first crash?

Test: tear down completely, re-up, observe the FIRST TMM container's startup before any restarts. If first-run is clean → cycle is self-reinforcing → workaround = clean `/shared/core` on each pod restart. If first-run still segfaults → cores are an effect not a cause.
