## The five fixes in `d994f08`

### 1. TMM mapres SIGSEGV — `internal/intent/cluster.go` defaults

| Setting | Before | After (aws-gpu-setup proven values) |
|---|---|---|
| TmmCpu | "4" | "2" |
| TmmMemory | "16Gi" | "8Gi" |
| PalCpuSet | "0-3" | "0,2" |
| TmmHugepages | "4Gi" | "4Gi" (unchanged) |

Live capture from the failing pod (`f5-tmm-bmws2 / f5-tmm-q9ts5`):

```
+ exec /opt/bin/mapres --tmm-tcl-file --tmm-args-name --allow-pipefail --info
<set_use_phys_mem> WARNING: Generic sock driver enabled. Disabling physical memory restriction...
<is_ht_environment> INFO: Detected HT Environment
<do_delay> WARNING: TMM_MAPRES_DELAY_MS remaining: 5000 ms
/bin/bash: line 1:    37 Segmentation fault      (core dumped) /opt/bin/init.tmm.sh
core config file does not exist
```

The "core file generated by the host; transitioning to idle mode" crashagent log line in the audit was a RED HERRING — that's crashagent reporting host core_pattern is configured, not evidence of a prior crash. The actual segfault is in `init.tmm.sh` at PID 37 after the 5s `do_delay`.

After live-patching the CNEInstance with cpu=2 / mem=8Gi / PAL=0,2, TMM went `5/7 Running` → `7/7 Ready, 0 restarts` in 25s. Tokyo's working BNK 2.3.0 CNEInstance + aws-gpu-setup's syd-test-lab both use these values — we were the outlier.

Three audit hypotheses ruled out conclusively during this session:
- **PCI BDFs**: kubectl debug confirmed `ens7→0000:00:07.0, ens8→0000:00:08.0` exactly as hardcoded.
- **cgroup v2**: `[ -e /sys/fs/cgroup/cgroup.controllers ]` confirmed v2 unified — AL2023 default — but TMM works fine on it once CPU/PAL are right.
- **First-boot clean cores**: the `tmm-core` volume is `emptyDir: {}`, per-pod fresh. No stale cores possible.

### 2. IRSA trust policy SA name mismatch — `internal/aws/phases/phase18_irsa_oidc.go`

Phase 18 was building the trust policy condition as `f5-cne-controller-<cluster>-serviceaccount`, but the actual SA created by Phase 21 / the `irsa-sa.yaml.tmpl` template (rendered with `InstanceNameCR = <cluster>-bnk`) is `f5-cne-controller-<cluster>-bnk-serviceaccount`. Missing `-bnk-` infix.

Effect: `sts:AssumeRoleWithWebIdentity` silently rejected the SA → `cloudProviderInstanceNil=<nil>` in cne-controller logs → `AssignPrivateIpAddresses` for the Gateway VIP never called → VIP never landed on BNK_EXT ENI even though TMM had the listener config.

Fix: line 73 of `phase18_irsa_oidc.go` now uses `"f5-cne-controller-" + name + "-bnk-serviceaccount"`. Test updated.

### 3. Bi-directional SG ingress — `internal/aws/phases/phase18_irsa_oidc.go`

Phase 18 already added one direction (cluster SG ← BNK_DATA, for TMM SNATted server-side packets reaching backend pods). Added the reverse (BNK_DATA ← cluster SG) for client traffic from pods to reach the Gateway VIP. New `ensureBNKDataSGIngress()` helper; test asserts both calls.

### 4. Missing GVR map entries — `internal/aws/phases/phase12_k8s_foundation.go`

`resolveGVR()` is a static map. It was missing slice-10's CRs (`F5SPKVlan`, `GatewayClass`). When Phase 23b called `applyRawYAML` to apply them, the function logged a warning `unknown apiVersion/kind` and returned `nil` — Phase 23b reported success while silently skipping both CRs. Result: TMM stayed at `RoutingDone=False` and `F5TmmAvailable=Pending`.

Fix: added `k8s.f5net.com/v1/F5SPKVlan` (plural `f5-spk-vlans`, namespaced) and `gateway.networking.k8s.io/v1/GatewayClass` (plural `gatewayclasses`, cluster-scoped).

**Followup**: replace static map with a live RESTMapper that refreshes after CRD installs — prevents recurrence for new CR types added in future slices.

### 5. Phase 25 readiness via conditions[] — `internal/aws/phases/phase25_activation_poll.go`

`isCNEReady()` checked only `.status.state ∈ {"Ready", "Running"}`. BNK 2.3.0 leaves `.status.state` empty and reports readiness via `.status.conditions[?(@.type=="Available")].status == "True"`. Without the fallback, Phase 25 times out at 40/40 even when CNEInstance is fully Available.

Fix: new `cneAvailableFromConditions()` helper; `isCNEReady()` also accepts `"Available"`.

### The canonical test pattern aws-gpu-setup uses

EC2 with **two ENIs**:
1. Primary ENI in mgmt/public subnet (10.0.1.0/24) — for SSH access via IGW + EC2 IMDS.
2. Secondary ENI in BNK_EXT (10.0.10.0/24) at e.g. `10.0.10.202` — for the curl path that reaches TMM.

SSH in via primary, `curl http://10.0.10.100/` — packet leaves via secondary (because dest is in 10.0.10.0/24), source IP is the BNK_EXT-side IP, arrives at TMM's BNK_EXT ENI on the same VPC subnet → no SG cross-subnet issues. **This is the only pattern that's been observed end-to-end working** (aws-gpu-setup syd-test-lab part-5: HTTP 200 615 bytes 11ms).

We also verified Tokyo's `aws-syd-test-cluster` (BNK 2.2.1 reference) uses the same client topology — control-plane configuration is consistent with both clusters.
