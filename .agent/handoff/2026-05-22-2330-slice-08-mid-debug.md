## TODOs to finish on the WIP branch BEFORE opening the PR

1. **Phase 11b: call `WaitForNodeHugepagesCapacity` after `WaitForDaemonSetReady`** — aws-gpu-setup waits up to 300s for the node's `.status.capacity.hugepages-2Mi >= TMM_HUGEPAGES`. The DS being Ready is not enough — kubelet must restart + re-advertise capacity (~10-30s). Without this wait, Phase 12+ proceed prematurely and f5-tmm pod scheduling fails with `Insufficient hugepages-2Mi`.

   Add to `internal/aws/phases/phase11b_ebs_csi_hugepages.go` after the existing `WaitForDaemonSetReady`:
   ```go
   tmmNode := st.Get("TMM_NODE_NAME")
   if tmmNode == "" {
       return fmt.Errorf("phase11b: TMM_NODE_NAME not in state (Phase 16 must run first)")
   }
   want := cl.Bnk.TmmHugepages // default "4Gi" after WIP commit
   fmt.Fprintf(os.Stderr, "[phase 11b] waiting for node %s to advertise hugepages-2Mi >= %s\n", tmmNode, want)
   if err := k8swait.WaitForNodeHugepagesCapacity(ctx, clients.K8s, tmmNode, want, 5*time.Minute); err != nil {
       return fmt.Errorf("phase11b: node hugepages capacity: %w", err)
   }
   ```

2. **Phase 11b: drop the custom gp3 StorageClass apply** — aws-gpu-setup uses the EKS-default in-tree `gp2` SC, which gets CSI-migrated after the addon installs. Don't apply a SC at all; the cluster already has gp2.
   - Remove the `gp3 StorageClass applied` apply step in `Phase11bEBSCSIHugepages`
   - Remove `gp3-storage-class.yaml` reference (the file can stay embedded for now, just unused)
   - Update state key — keep `GP3_STORAGE_CLASS` write but set it to the actual default SC name (read via `kubectl get sc -o jsonpath` style — but we don't have that helper; simplest: `st.Set("GP3_STORAGE_CLASS", cl.Bnk.StorageClassName)` which is now "gp2")
   - Optionally: rename state key to `BNK_STORAGE_CLASS` for clarity
   - Update Phase 11b down to NOT delete the gp2 SC (it's EKS-owned)
