Introduction & Mental Model

awsbnkctl provisions an F5 BNK (BIG-IP Next for Kubernetes) data path on AWS EKS from a single cluster.yaml, then lets you run protocol walkthroughs, capability scenarios, and AI inference benchmarks on top. The tool handles the full lifecycle: VPC plumbing, EKS nodegroups, BNK activation, forge registration, and controlled tear-down — so you can focus on what BNK can do, not how to get it running. 

cluster.yaml  ──(awsbnkctl up -f)──►  live BNK cluster  ──►  run demos / scenarios / benchmarks
 (the blueprint)                       (the data path)        (what you show / measure)

1. Workflow: Stand Up an Environment

Follow these steps for any environment. The commands below use the examples/demo/cluster.yaml canonical demo config as the reference.

  1. Authenticate to AWS

    aws sso login --profile <your-profile>
aws sts get-caller-identity

  2. Provide F5 supply-chain files

    The bnk: block in cluster.yaml references a far-archive and a JWT that are gitignored / local. Place them on disk before running. For AI runs, the Hugging Face token is read inline rather than from a dotenv file:

    HF_TOKEN=$(cat .hf_token)

  3. Validate the config — no AWS calls made

    awsbnkctl validate examples/demo/cluster.yaml

  4. Dry-run the plan — AWS credentials required, no mutations

    awsbnkctl up --config examples/demo/cluster.yaml --dry-run

  5. Provision — --config has shorthand -f

    awsbnkctl up --config examples/demo/cluster.yaml

    Full AI-rig invocation with credentials inline:

    HF_TOKEN=$(cat .hf_token) AWS_PROFILE=<profile> ./awsbnkctl up -f examples/ai-rig/cluster.yaml

  6. Run demos, scenarios, or benchmarks — see Sections 4–6 below.

  7. Tear down

    awsbnkctl down --config examples/demo/cluster.yaml --yes
Resumability: State is written to .awsbnkctl/<cluster-name>/state.env after every successful phase. A mid-run failure is safe to resume by re-running up with the same config.
Kubeconfig isolation: The admin kubeconfig is fetched to .awsbnkctl/<cluster-name>/kubeconfig. Always set KUBECONFIG=.awsbnkctl/<cluster-name>/kubeconfig before running kubectl-style commands. Important: awsbnkctl k get without -f/--config uses your host kubeconfig, not the cluster kubeconfig — this can produce misleading output if you have another cluster active on the host.

2. Choosing a cluster.yaml

The pattern: field in cluster.yaml selects the BNK interface topology. Valid values are:

  • external-only — single external (ingress) interface, CNI backend.
  • dual-interface — external + internal TMM interface, CNI backend. The legacy alias host-device is normalized to this at load. Requires network.dataPath external and internal subnets and a nodegroup of ≥3 nodes.
  • sriov-external — single external interface via SR-IOV / vfio-pci (experimental).
File Cluster Name Pattern Default VIP Best For
examples/demo/cluster.yaml bnk-demo host-device (dual-interface) 10.0.10.100 All-rounder. Full external+internal TMM, demo mode (24h TTL), forge link. Best for protocol show-and-tell.
examples/ai-rig/cluster.yaml ai-rig external-only 10.0.10.100 Benchmarking. GPU nodegroup (g5.xlarge) + SageMaker/vLLM (LMI). The AI inference + proxy-shootout rig.
examples/external-only/cluster.yaml bnk-extonly external-only 10.0.10.100 Ingress-only, simplest and cheapest, no internal TMM subnet.
examples/full-cluster/cluster.yaml full-cluster host-device 10.0.10.100 Complete reference config, external + internal, full BNK stack.
examples/sriov-external/cluster.yaml bnk-sriov sriov-external 10.0.10.100 Experimental DPDK / vfio variant; ENA bound to vfio-pci via a node-prep DaemonSet.
examples/tracer/cluster.yaml tracer network-only (n/a) Tracer-bullet: minimal VPC plumbing only — no EKS, no IAM, no BNK. Smoke test.
metadata.name is load-bearing. It becomes the awsbnkctl:cluster=<name> tag on every AWS resource and the directory name under .awsbnkctl/. metadata.region must be set explicitly — there is no default region.

3. Three Families of Things to Run

After up completes, there are three top-level command families:

  • Show & Tell awsbnkctl demo … — curated protocol walkthroughs (internal/demo/).
  • Validation awsbnkctl scenarios … — capability / validation scenarios with Green / Amber readiness ratings (internal/scenarios/).
  • Benchmark awsbnkctl forge benchmark … — aiperf load tests and the Envoy-vs-BNK proxy shootout.

Each demo and scenario owns a dedicated VIP so they never collide with each other.

6. awsbnkctl forge benchmark — AI Load Testing & Proxy Shootout

Runs aiperf against the BNK Gateway VIP from the jumphost (the only host with in-network access to the external VLAN), then pushes structured results to forge (POST /api/benchmarks/results). The jumphost is reached via EC2 Instance Connect (EICE) — your IAM principal needs ec2-instance-connect:SendSSHPublicKey and the aws CLI on PATH. One-time on the jumphost: pip install aiperf (or pass --ensure-aiperf).

Four Run Modes

  1. Single-run — explicit --concurrency / --num-requests / --isl / --osl / --stream.
  2. Preset mode — --scenarios latency,throughput (or all); presets: latency, throughput, long-context, streaming. Per-explicit flags are ignored when set.
  3. Native forge scenario — --scenario baseline expands into N ordered child aiperf runs; mutually exclusive with --scenarios.
  4. Proxy shootout — --proxies envoy,f5-bnk,… runs the chosen scenario once per front-end for an apples-to-apples comparison.

Worked Example: Proxy Shootout

awsbnkctl forge benchmark \
  --region ap-southeast-2 --instance-id <jumphost-id> --vip 10.0.10.100 \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --host-header awsbnkctl-aiinference.local \
  --scenario baseline \
  --proxies envoy,f5-bnk \
  -f examples/ai-rig/cluster.yaml

On success, one JSON line per run is emitted containing run_id, proxy, model, status, and p50/p99 latency, RPS, and TPS.

Known limitation — proxy auto-deploy: Today the benchmark discovers proxy front-ends but does not auto-deploy them. An operator must create the proxy in forge (e.g. POST .../proxies) before an Envoy shootout run. Building auto-deploy into the CLI is the remaining gap to a true single-command shootout.

7. Tear Down & Flag Reference

awsbnkctl down --config <file> --yes deletes the AWS infrastructure and forge artifacts (target + proxies + agent), but saved benchmark runs are preserved in forge.

down Flags

FlagTypeDefaultDescription
--config, -fstring""Path to cluster.yaml (required)
--yesboolfalseSkip the interactive destroy confirmation (required with --config)
--autoboolfalseSkip the destroy confirmation
--dry-runboolfalsePrint what would be destroyed, make no AWS mutations
--keep-forge-linkboolfalsePreserve forge-link.json on down (skips forge unregister)
--keep-irsaboolfalseRetain the OIDC provider and IRSA role on down (kept for reuse across cluster iterations)

up Flags

FlagTypeDefaultDescription
--config, -fstring""Path to cluster.yaml (required)
--dry-runboolfalsePrint the phased plan and exit 0 with no AWS mutations
--autoboolfalseSkip the confirmation prompt before apply
--demoboolfalseProvision the same cluster marked as a demo (writes DEMO_MODE; requires testing.jumphost.enabled)
--register-with-forgeboolfalseAfter a successful apply, register the EKS cluster with bnk-forge over MCP
--no-kubeconfigboolfalseSkip the post-apply admin kubeconfig fetch
--skip-activation-pollboolfalseSkip the 20-minute CNEInstance + License activation poll
