Mirroring FAR into Artifactory

A self-hosted JFrog Artifactory on a single IBM Cloud virtual server, holding a complete, digest-verified copy of everything a BNK install pulls — so an air-gapped cluster installs from a registry you control.

No Kubernetes cluster is involved. registry replicate copies registry-to-registry, so the mirror can be filled long before any cluster exists — which is the point, because the cluster that needs it cannot reach the internet.

Before you start

01
Your workstation

What you need to hand

An IBM Cloud API key with permission to create VPC resources, a DNS name you can point at a new floating IP, and the roksbnkctl binary. The API key is used for exactly one thing here — resolving the F5 pull credential — and no IBM Cloud resource is modified by the mirror itself.

Stand up Artifactory

02
Your workstation

Create the server

One script creates an isolated VPC, a subnet, a public gateway, a security group, and a single virtual server. On that server it runs three containers: Artifactory, a PostgreSQL database, and Caddy for TLS. Nothing outside that VPC is touched.

Why a database container

Artifactory requires PostgreSQL. Its Access service refuses to start against the embedded Derby database — DB Type derby is not allowed — so a single-container deployment never comes up, however long you wait for it.

The failure is worth recognising because it does not look like a database problem: Artifactory's own API answers on 8081 while Access never binds 8046, and every other service sits in a Cluster join: Retry N loop that reads exactly like slow startup. The script handles this for you; the note is here for anyone adapting it.

# point this at a DNS name you can update
export ART_DOMAIN=artifactory.example.com
export IBMCLOUD_API_KEY=...

# optional — defaults to region us-east, resource group "default"
export ART_REGION=us-east
export ART_RESOURCE_GROUP=default

./scripts/demos/lib/deploy-artifactory-vsi.sh
Resource group names are case-sensitive

default is not Default. If the name does not exist the script stops and lists the groups your account does have, with the account default marked — set ART_RESOURCE_GROUP to one of those. Run ibmcloud resource groups to see the same list yourself.

The script prints the floating IP as soon as it has one, then waits for Artifactory to answer over HTTPS. Point your DNS name at that IP while it waits. First boot takes roughly ten minutes: PostgreSQL initialises, then Artifactory creates its schema.

The script also generates Artifactory's two startup secrets — its master key and join key — and writes them before the first boot. They are not optional and Artifactory does not create them itself in a container deployment; starting without them leaves the database in a state that only a wipe recovers.

If it never finishes

By far the most common cause is DNS: Caddy cannot obtain a certificate until the name resolves to the server, and inbound port 80 must be open for the ACME challenge. Confirm with getent hosts $ART_DOMAIN — it must return the floating IP the script printed. (dig is not installed everywhere; when it is missing it fails with command not found, which looks just like a name that does not resolve.)

03
Nothing to do

The server configures itself

There are no console steps. The virtual server writes an artifactory.config.import.yml before Artifactory first starts, and Artifactory applies it during initialisation:

version: 1
GeneralConfiguration:
  eula:
    accepted: true
OnboardingConfiguration:
  repoTypes:
    - docker
    - helm

That accepts the licence agreement and creates the repositories. You can watch it happen in the container log:

OnboardingYamlBootstrapper - Bootstrapping artifactory from artifactory.config.import.yml
OnboardingYamlBootstrapper - Creating default repositories for docker
OnboardingYamlBootstrapper - Creating default repositories for helm
OnboardingYamlBootstrapper - Configuration reloaded
On JCR this is the only way, not merely the convenient one

Creating a repository over REST answers 400 This REST API is available only in Artifactory Pro, and the EULA endpoint the web console itself calls returns 404. Without this file the console shows a No signed EULA banner and returns server errors, with no working way to clear it.

The schema is small and fixed: eula.accepted takes a boolean, and repoTypes takes a list of package types. There is no field for repository names, so each type gets JFrog's defaults — docker-local, docker-remote, docker, helm-local, helm.

If you would rather mirror into a repository with a name of your choosing, create one in the console (Administration → Repositories → Add Repository → Local → Docker) and point ART_REPO at it. Both are one config field apart and both are verified; docker-local is the default here only because it needs no console step.

04
Recommended, not required

Change the administrator password

The mirror works with the initial credentials, so this does not block anything. Do it anyway: the server is on the public internet — it has to be, because its certificate is obtained over a challenge that reaches it from outside — and until you change it, anyone who finds the hostname has administrator access with the well-known default.

Sign in at https://artifactory.example.com as admin / password and set a new one. If the instance will outlive the demonstration, also narrow the security group: port 80 must stay open for certificate renewal, but 443 and 22 can be restricted to the addresses you work from.

Generate a token first, then change the password

An access token is not derived from the account password — it is a signed credential validated independently — so rotating the password does not invalidate it. Verified on this deployment: after the change, the old password returned 401 while the same token still returned 200 against the REST API, the Docker /v2/ endpoint and the repository catalogue, and registry verify still passed.

That is the reason to prefer a token for the mirror: the credential you hand to a pipeline keeps working when the login you use in the browser changes. Generate it with the initial credentials, put it in ART_TOKEN, then change the password.

curl -u admin:'<password>' -X POST \
  -d username=admin -d scope=applied-permissions/user -d expires_in=0 \
  https://artifactory.example.com/artifactory/api/security/token

expires_in=0 issues a non-expiring token. A bare request without scope fails with Insufficient scope.

Why there is no dedicated mirror user

Artifactory's users, groups and permission targets are licensed Pro features; on JCR their REST APIs answer 400 … only in Artifactory Pro and the screens are absent. There is no scoped identity to create, so the mirror authenticates as admin. That is reasonable for a demonstration or a single-purpose mirror host, and not what you want for a shared registry — on Pro or Enterprise, create a user, grant it read and write on the repository through a permission, and use that instead.

Mirror it — interactively

05
roksbnkctl

Point a workspace at the repository

Create a mirror-only workspace — cluster.create: false means no cluster is ever built — then set the four fields that select the target.

roksbnkctl -w art registry target generic
roksbnkctl -w art registry target generic_host        artifactory.example.com
roksbnkctl -w art registry target generic_repo_prefix bnk-mirror
roksbnkctl -w art registry target generic_username    admin          # JCR: admin is the only identity

# the token on stdin — never as an argument
echo "$ART_TOKEN" | roksbnkctl -w art registry target generic_password --password-stdin

An argument is visible in ps output, in shell history, and in a terminal recording. --password-stdin exists so the token is in none of them.

Addressing

roksbnkctl composes references as <host>/<prefix>/<image>, which is Artifactory's repository-path method. If your instance is configured for the subdomain method instead, put the full subdomain in generic_host and leave generic_repo_prefix empty. Getting this wrong produces a 404 that reads like a bad prefix and sends you looking in the wrong place.

06
roksbnkctl

Replicate, then verify

roksbnkctl -w art registry bom        # what BNK needs — offline
roksbnkctl -w art registry diff       # what is missing right now
roksbnkctl -w art registry replicate  # copy it, by digest
roksbnkctl -w art registry verify     # prove it
Gate on verify, not on diff

A workspace records what it last replicated, and that record can describe a registry that has since been rebuilt or replaced. In that state diff has been observed reporting "mirror is in sync" against an empty registry, while verify correctly reported every artifact missing. If a workspace has been re-pointed at a different registry, trust verify.

Verify is the step that means anything. replicate reports what it pushed; verify independently re-reads the bill of materials and checks every artifact against the digest it should have, so a partial copy or a tag that moved underneath you is caught here rather than at install time.

If replicate stops partway

The copy is per-artifact, so it fails partway rather than cleanly — usually a repository quota or a filestore near capacity. Run diff to see what actually landed, then replicate again; it copies only what is missing.

Mirror it — unattended

07
Container

The same work, with no config file

Steps 6 and 7 are the interactive path an operator uses to test a mirror. In a pipeline the same binary runs the same verbs in a container, with no config.yaml anywhere — every setting arrives as an environment variable, because a CI runner has no shell, no prompts, and nowhere to stage a file.

Each field maps one-to-one onto the command you just ran by hand:

InteractiveUnattended
registry target generic_hostROKSBNKCTL_GENERIC_HOST
registry target generic_repo_prefixROKSBNKCTL_GENERIC_REPO_PREFIX
registry target generic_usernameROKSBNKCTL_GENERIC_USERNAME
registry target generic_passwordROKSBNKCTL_GENERIC_PASSWORD

Put them in a secret, keeping the token off the command line here too:

printf '%s' "$ART_TOKEN" | kubectl -n bnk-ci create secret generic artifactory-mirror \
  --from-literal=host=artifactory.example.com \
  --from-literal=repo=bnk-mirror \
  --from-literal=username=admin \
  --from-file=password=/dev/stdin
08
Argo Workflows

Run it as a workflow

The supplied workflow runs the same five verbs as pipeline steps, and gates on verify rather than on replicate.

argo submit -n bnk-ci --wait wf-artifactory-mirror.yaml

It is deliberately self-contained: it reads the one secret above rather than any wider configuration, so it can be applied to any cluster already running Argo Workflows. There is no teardown on failure — a failed run leaves its workspace in place so the next one resumes, and because replicate skips artifacts already present at the right digest, a re-run costs only what did not land.

What success looks like

Both paths end on the same two lines. The second one is the one to gate on:

✓ mirrored 89 artifacts into artifactory.example.com/<your-repo>
✓ all 89 BOM artifacts present + digest-matched in the mirror
Browse the result at https://artifactory.example.com/ui/repos/tree/General/bnk-mirror. To empty the mirror without touching the server, run roksbnkctl -w art registry delete.
