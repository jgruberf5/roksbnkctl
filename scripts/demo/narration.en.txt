Preparing a fresh Ubuntu|We start on a freshly provisioned Ubuntu 24.04 server on IBM Cloud. rocks BNK cuddle only requires Terraform and helm to be installed locally — everything else is built in.
Installing roksbnkctl|We download the latest rocks BNK cuddle release binary and install it — one self-contained binary, no toolchain required.
Configuring the workspace|The entire deployment is described by a single declarative config file. We seed the workspace from it, with no interactive prompts.
runner container|The runner container bundles everything rocks BNK cuddle needs — Terraform, helm, and all the tooling are already inside it, so nothing has to be installed on the host. A single docker run does everything a CI job needs.
Configuring declaratively|The entire deployment is one declarative config file, checked into the repository. There are no prompts, and secrets stay in the CI environment.
Build the ROKS cluster|We could build every phase automatically, in one step and with no interaction, using a single rocks BNK cuddle up. But in this demonstration we drive each phase independently. We begin by building the cluster. You could instead point rocks BNK cuddle at the name of an existing IBM ROKS cluster.
Register with BNK Forge|At this point we can register our IBM ROKS cluster with BNK Forge. Let's do that.
Install BIG-IP Next|Next we install big IP next for cuber net tees, and license it.
testing framework|Next we build out the testing framework host, and run basic tests.
Remove BIG-IP Next|Now we remove big IP next for cuber net tees by downing that phase. The cluster keeps running.
Rebuild BIG-IP Next|Now we can independently rebuild the big IP next for cuber net tees phase — for example, to test a new version — on the same running IBM ROKS cluster.
Remove all phases|Finally, a single down command removes any or all of the phases — including the cluster itself.
Back where we started|We are back where we started, using rocks BNK cuddle as a single-binary deployment tool.

# ── Demo #3 (far-demo.sh): mirroring FAR into a private OCI registry ─────────
Preparing the demo host|An air-gapped cluster cannot reach the F5 Artifact Repository, so every chart and image a deployment needs must first be copied into a registry you control. We start on a plain Ubuntu host; the only dependency rocks BNK cuddle adds is helm, which it uses to pull the classic-Helm charts in the bill of materials.
Install the roksbnkctl binary|We install the same single rocks BNK cuddle binary. The mirror is built in — there is no separate tool to learn.
Seed a workspace for the mirror|The workspace needs only three things to mirror: the manifest version for big IP next for cuber net tees, the address of the F5 Artifact Repository, and the name of the auth tarball that unlocks it. Notice there is no credential in this file, and no cluster is created. Replication reads the manifest, pulls from F5, and pushes to your registry — a running cluster is never involved.
Pull the FAR credential from COS|So where does the credential come from? It is an auth tarball in the orchestration bucket on IBM Cloud Object Storage, and rocks BNK cuddle reads it straight from there. Here it lists the bucket, and there is the F5 far auth key tarball. Notice the bucket lives in the us south region while our workspace does not — rocks BNK cuddle resolves each bucket's own region, so this just works. The credential is never pasted into a config, never typed, and never leaves as a file.
The bill of materials|Now rocks BNK cuddle pulls that auth tarball from COS to authenticate, reads the F5 manifest, and derives the exact bill of materials — every chart and every image the install will pull, pinned by digest. Eighty-eight artefacts: sixty-two images and twenty-six charts. That is the contract the mirror has to satisfy.
Point the workspace at the mirror|Our target is a standard open-source Harbor registry, already running. Any O C I compliant registry would do — rocks BNK cuddle does not care which. Four fields select it: the kind, the host, the project the artifacts nest under, and the user. The password is piped in on standard input, so it never appears in the command line or in your shell history. Read it back, and the password shows only as set.
What replication would copy|Diff compares the bill of materials against what the mirror already holds, so you can see exactly what a replication would move before you move it. Our registry is brand new, so every artifact is missing.
Replicate FAR into the mirror|Now we copy. Each chart and each image is fetched from the F5 Artifact Repository and pushed into the registry by digest, so the copy is bit for bit identical to the source. Anything already present is skipped, which makes replication safe to re-run and cheap to resume.
Verify every mirrored artifact|Copying is not the same as being correct. Verify walks the bill of materials again, and for every single artifact confirms it is present in the mirror and that its digest matches the source exactly.
Browse the mirror|Every chart and every image that a big IP next for cuber net tees install needs now lives in a registry you control. From here, an air-gapped install pulls from this host and never reaches out to F5 — with one rocks BNK cuddle workspace, and no cluster.
